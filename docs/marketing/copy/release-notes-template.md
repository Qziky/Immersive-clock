# 发布说明模板

发布说明面向用户解释“发生了什么、为什么值得更新、是否需要操作”。提交记录和技术实现可以链接到技术文档，不应直接倾倒到用户公告中。

## 完整模板

```markdown
# 沉浸式时钟 [版本号]

> 发布日期：[YYYY-MM-DD]

[用 1–2 句话说明本次版本主题和最重要的用户价值。]

## 主要变化

- **[变化标题]**：[用户现在可以完成什么，或体验有何改善。]
- **[变化标题]**：[避免只写组件名、函数名或内部重构。]
- **[变化标题]**：[若有前提，直接说明权限、平台或网络要求。]

## 体验改进

- [可感知的交互、可读性、性能或无障碍改进。]

## 问题修复

- 修复 [触发条件] 下 [用户看到的问题]。
- 修复 [数据、计时或显示问题]，避免 [影响]。

## 数据、权限与兼容性

- 本地数据：[自动兼容 / 需要备份 / 需要重新配置的具体说明]。
- 权限：[是否新增或改变麦克风、定位、通知权限使用]。
- 平台：[Web/PWA/Windows/Linux 的差异及实际发布附件]。
- 已知限制：[确有必要才填写；同时给出规避方法。]

## 如何更新

- Web：[刷新、等待更新提示或清缓存的准确步骤]。
- PWA：[适用步骤]。
- 桌面版：[下载附件、覆盖安装或卸载要求]。

## 反馈

如遇问题，请提供设备、系统、浏览器或桌面版本、复现步骤和截图。请勿公开上传包含位置、课程安排或备份数据的文件。
```

## 应用内公告短版

```markdown
# [版本主题]

[一句话说明最重要的变化。]

## 新增与改进

- [变化一]
- [变化二]
- [变化三]

## 修复

- [最重要的修复]

> [如无额外操作：本次更新无需迁移，现有本地设置会继续保留。]
```

## 写作规则

- 标题先写用户结果，如“课程导入会在保存前提示错误”，不要只写“重构 ScheduleEditor”。
- 将“新增”“改进”“修复”分开，避免所有条目都写成“优化”。
- 数据迁移、权限变化、备份格式变化和平台下线必须显著展示。
- 不写没有测量依据的“性能提升 50%”“全面更稳定”。
- 已知限制只记录真实、可复现且会影响用户决策的问题。
- 安全问题的披露范围应与修复状态和维护者决策一致，不在修复前公开可利用细节。

## 发布前核对

- [ ] 版本号、发布日期和下载附件一致。
- [ ] Windows/Linux 支持与当前发布产物一致，未误写 macOS 安装包。
- [ ] 截图来自本次版本，设置导航和功能名称没有漂移。
- [ ] 噪音、天气、隐私和离线能力使用了正确限定语。
- [ ] 数据迁移、权限请求和不可逆操作已说明。
- [ ] 所有链接可访问，反馈入口仍有效。
- [ ] `public/docs/announcement.md` 与 `public/docs/changelog.md` 各自承担公告和历史记录，没有复制冲突。
